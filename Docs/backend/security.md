# Backend security

Two authentication systems, three roles, four rate-limit keys, and an audit trail on reads.

Source: `Backend/src/middleware/`, `Backend/src/config/auth.ts`, `Backend/src/utils/token.ts`.

---

## 1. Two authentication systems that never meet

| | Agents | Humans |
|---|---|---|
| Credential | Per-device API key, 32 random bytes | Better Auth session |
| Presented as | `Authorization: Bearer <key>` | Session cookie or bearer token |
| Middleware | `deviceAuth` | `userAuth` |
| Attaches | `req.device` | `req.user` + `req.session` |
| Routes | `/api/v1/*` | `/v1/dashboard/*` |
| Lifetime | Until re-enrollment or deactivation | Session expiry or revocation |

**They must never share middleware.** The prefixes make the flow obvious at a glance. If you are
adding a route and unsure which it belongs to, ask whether a *machine* or a *person* calls it -
that answer decides it.

The failure this prevents: a stolen device key reading everyone's reports, or a stolen dashboard
session injecting fabricated activity.

## 2. Credential handling

Nothing is stored in a form that can be presented.

| Credential | Stored as | Generated by |
|---|---|---|
| Device API key | `HMAC-SHA256(pepper, key)` in `devices.apiKeyHash` | `crypto.randomBytes(32)` |
| Enrollment token | `HMAC-SHA256(pepper, "enrollment:" + token)` in `organizations.enrollmentTokenHash` | `crypto.randomBytes(24)` |
| User password | Better Auth's own hashing | Better Auth |

The **domain-separation prefix** on enrollment tokens means one can never collide with - or be
replayed as - a device API key, even though both use the same pepper.

Both raw values are returned to the caller **exactly once** and never again. `npm run seed` prints
the enrollment token; if it is lost, rotate rather than recover.

`DEVICE_TOKEN_PEPPER` has a development default so local work runs without a `.env`. The server
**refuses to start in production** if that default is still in place - shipping it would let anyone
forge a device key hash offline.

Lookup is by HMAC on a unique indexed column, so credential checks are a single indexed read and
inherently constant-time with respect to the presented key. `safeEqualHex` exists for the cases
where a digest must be compared in application code.

## 3. Roles

Three roles, checked by `requireRole(...)` on every dashboard route.

| Capability | `super_admin` | `manager` | `auditor` |
|---|---|---|---|
| View reports, roster, overview | Yes | Yes | Yes |
| View alerts and USB events | Yes | Yes | Yes |
| **View screenshots** | Yes | Yes | **No** |
| Edit employees, assign devices | Yes | No | No |
| Edit policy and categories | Yes | No | No |
| Rotate the enrollment token | Yes | No | No |
| Deactivate a device | Yes | No | No |
| Force a device to sync | Yes | No | No |

A 403 names `requiredRoles` and `currentRole`, which makes a misconfigured account obvious in a
log rather than a mystery.

**Auditor exclusion from screenshots is structural** (AD-12), applied to both the index and the
image bytes. An auditor gets aggregate reports and the audit log, never a picture of someone's
desktop.

`userAuth` also returns **403 for a deactivated account**, distinct from 401 for a missing or
expired session. The dashboard treats them differently.

## 4. Rate limiting

Fixed window, in-process, with a **caller-chosen key**. That last part is the important one.

| Route | Limit | Keyed by |
|---|---|---|
| `POST /api/v1/device/enroll` | `RATE_LIMIT_ENROLL_PER_MIN` (10) | **MachineGuid from the body** |
| `POST /api/v1/events/:channel` | `RATE_LIMIT_INGEST_PER_MIN` (200) | Device row id (post-auth) |
| `POST /api/v1/screenshots` | `RATE_LIMIT_SCREENSHOT_PER_MIN` (60) | Device row id |
| `GET /api/v1/heartbeat` | 120 | Device row id |
| `GET /api/v1/policy` | `RATE_LIMIT_INGEST_PER_MIN` (200) | Device row id |
| `POST /api/v1/consent` | 60 | Device row id |
| Everything under `/api/v1` | `RATE_LIMIT_UNAUTHENTICATED_PER_MIN` (3000) | IP, pre-auth backstop |
| Dashboard login/register | 10 | IP |

**Why the keys matter more than the numbers:** an office of 100 machines shares one public
address. Keyed by IP, the enrollment limit of 10/min would have applied to the entire company, and
one busy workstation would throttle its ninety-nine neighbours.

Enrollment is keyed on the MachineGuid **in the request body**, falling back to IP when the body
has no `deviceId` - a malformed request should still be limited, just not able to escape limiting
by omitting a field.

`deviceAuth` runs **before** the per-device limiter, because the limiter keys on the device it
resolves. The unauthenticated backstop covers everything before that.

`req.ip` is used, never `x-forwarded-for` directly. That header is client-supplied; `req.ip` only
derives from it when `TRUST_PROXY` declares a proxy in front. **Set `TRUST_PROXY` correctly or
per-IP limiting breaks in one direction or the other** - see
[../reference/configuration.md](../reference/configuration.md#trust_proxy).

Buckets are swept lazily every 1000 requests rather than on a timer, which would keep the event
loop referenced and complicate shutdown. Counters are scoped per `rateLimiter(...)` call, not
module-wide, so routes with different limits do not collide on one counter.

**Scope:** counters are per process, in memory. Correct for a single instance; with N replicas the
effective limit is N times the configured one. An accepted trade for not requiring Redis, since
these limits exist to contain a stuck agent rather than to meter anything (AD-08).

A 429 body names the limit and `retryAfterSeconds`. The agent backs off exponentially on any
non-success, so a 429 during a mass rollout self-heals.

## 5. Audit logging

`auditLogger(action, getTarget?)` writes to `audit_logs` on response `finish`, **only for 2xx**
and only when a user is attached.

Reads are audited, not just writes - who looked at whom is the point of the trail. Screenshot
views are audited **individually**, which is why the image has its own route rather than being
served from the index.

Actions in use: `VIEW_OVERVIEW`, `VIEW_EMPLOYEE_ROSTER`, `VIEW_TEAM_ATTENDANCE`, `VIEW_EMPLOYEE_DETAIL_REPORT`,
`VIEW_EMPLOYEE_ACTIVITY_LOG`, `VIEW_ALERTS`, `VIEW_USB_EVENTS`, `VIEW_SCREENSHOT_INDEX`,
`VIEW_SCREENSHOT`, `VIEW_DEVICE_INVENTORY`, `ASSIGN_DEVICE`, `SET_DEVICE_STATUS`,
`VIEW_ALL_EMPLOYEES`, `VIEW_EMPLOYEE_DETAIL`, `CREATE_EMPLOYEE`, `BULK_CREATE_EMPLOYEES`,
`UPDATE_EMPLOYEE`, `VIEW_ALL_ORGANIZATIONS`, `VIEW_ORGANIZATION_DETAIL`, `CREATE_ORGANIZATION`,
`ROTATE_ENROLLMENT_TOKEN`, `VIEW_POLICY`, `UPDATE_POLICY`, `VIEW_CATEGORIES`, `UPSERT_CATEGORY`,
`DELETE_CATEGORY`.

A failure to write an audit row is logged but does not fail the request - it runs after the
response has already been sent.

## 6. Other protections

- **Helmet** for security headers, **CORS** restricted to `FRONTEND_URL` with credentials.
- **Body limit** `JSON_BODY_LIMIT` (2 MB). The 413 response names the limit, the received size and
  the remedy, because the agent logs the body verbatim.
- **Error handler** logs 5xx with a stack and 4xx as a one-line warning. A 4xx is the API doing its
  job; printing a stack trace for each one buries the 5xx that needs attention. Stacks are returned
  to the client in development only.
- **Device kill switch**: `isActive = false` gives 403 on every authenticated route, on the socket
  handshake, and at re-enrollment. Reinstalling is not a way around it.

## Failure modes

| Symptom | Likely cause | Check |
|---|---|---|
| Every login fails opaquely | `express.json()` mounted before the Better Auth handler | Middleware order in `server.ts` |
| Whole office rate-limited together | `TRUST_PROXY` too low behind a proxy | [../reference/configuration.md](../reference/configuration.md#trust_proxy) |
| Limits trivially bypassed | `TRUST_PROXY` set with no proxy in front | Same |
| Server refuses to start in production | `DEVICE_TOKEN_PEPPER` still the dev default | `.env` |
| Agent gets 401 after working | Key rotated by re-enrollment elsewhere, or pepper changed | Changing the pepper invalidates **every** device key |
| Agent gets 403 | Device deactivated | Devices screen |
| Audit log empty | Response was not 2xx, or no user attached | `auditLogger` only fires on success |
